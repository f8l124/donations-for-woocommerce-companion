# v1.2.0 — Goal-Aware Giving

Two opt-in features that read the parent plugin's campaign goal and shape donor behavior:

1. **Dynamic max from remaining goal** — clamp the donor's max custom amount to (goal − raised) so a one-time donor can give up to fully funding the campaign but no more.
2. **Fully-funded affordance** — when a campaign reaches its goal, show donors a "Goal met! Support our general fund" card with a one-click route to a configured general-fund campaign.

Both off by default. Existing v1.1.x sites see zero behavior change until admin opts in via *WooCommerce → Donations Companion → Settings → Goal-aware giving*.

## Why this exists

Two real nonprofit pain points:

- **Donor side:** "I want to fully fund this campaign — how much is left?" Currently the donor reads the parent's progress bar and does mental math. With dynamic max, the donor sees the form's max auto-update to remaining-goal, and any custom amount above that is rejected.
- **Admin side:** "Our school-construction campaign hit its goal three weeks ago, but donors keep giving to it. Now we have to manually allocate the overflow." With the fully-funded redirect, the donor is offered the org's general fund as a natural alternative when a specific campaign closes.

The features compose; admins typically enable both. Each ships independently if the org's flow demands it.

## Architecture

### `Config\Goal_State`

Read-only view onto the parent plugin's goal-tracking surface:

```php
$state = Goal_State::for_campaign( $campaign_id );
$state->is_amount_goal();   // true for fixed_amount + percentage_amount with non-zero target
$state->goal_amount();      // dollar target
$state->raised_amount();    // total_donation_amount + fixed_initial_amount (mirrors parent's progress formula)
$state->remaining_amount(); // max(0, goal - raised)
$state->is_fully_funded();  // raised >= goal AND amount-goal AND goal > 0
$state->clamp_max( $max );  // shared utility: min($max, $remaining) when not fully funded
```

Reads (no writes):

- `wc-donation-goal-display-option` / `-display-type` / `-fixed-amount-field` / `-fixed-initial-amount-field` — campaign post meta
- `wc_donation_product` → `total_donation_amount` — linked product post meta

Per-request cached via static map. Tests reset via `Goal_State::reset_cache()`.

### Server + client clamp share one source of truth

Both `Frontend\Renderer::build_form_config` (donor-side max shipped to overlay JS) and `Frontend\Submit_Guard::enforce` (server-side validation) call `Goal_State::clamp_max()` so the two layers cannot drift.

Donor-side: form rejects amounts above clamped max client-side. Server-side: re-validates on submit; donors who bypass the client-side check (DevTools, curl) get HTTP 422.

### Recurring intervals not clamped (documented behavior)

Reasoning: the donor's first charge fits within remaining, but their renewals exceed it within months. Silently capping renewals is worse than letting the goal be modestly exceeded. Recurring intervals continue to use their configured max from the campaign / template / global layers.

If the campaign is fully funded AND the admin enables strict mode, recurring submits are rejected too — at that point the campaign is closed.

### Fully-funded card

When `is_fully_funded()` returns true AND the admin configured a general-fund campaign, the renderer adds two attributes to the overlay wrapper:

```html
<div data-dfwc-overlay-target
     data-fully-funded="1"
     data-general-fund-url="https://example.org/donate/general-fund/"
     ...>
```

The overlay JS reads these and renders a green card above the form with a CTA linking to the general fund. Default mode: form still accepts donations to the funded campaign. Strict mode: Submit_Guard rejects with a friendly redirect message.

## Admin UI

`WooCommerce → Donations Companion → Settings → Goal-aware giving` adds three fields:

| Field | Default | Behavior |
|---|---|---|
| Cap the donor's max custom amount at the campaign's remaining goal | off | Toggles the dynamic-max feature globally |
| Reject donor submissions when the campaign is fully funded | off | Toggles strict mode (block + redirect) |
| General fund campaign | none | Dropdown of all `wc-donation` posts; picks the redirect target |

The dropdown sanitizer validates the picked campaign exists and is the right post type; stale ids reset to 0 silently.

## Per-currency presets (Phase 6) interaction

Goal is denominated in base currency. Clamp resolves in base currency for donors in any currency via WCML's exchange rate at render time. Tiny rejections at the threshold can happen if WCML's rate fluctuates between render and submit; the donor's error message tells them the actual cap.

## Test coverage

201 → 214 cases, 518 → 552 assertions.

New `Goal_State_Test` (13 cases) covers:

- No goal returns 0 everywhere
- Non-amount goal types are not amount goals
- Fixed-amount goal with no donations
- Initial seed counts toward raised
- Actual donations add to raised
- Fully funded when raised meets / exceeds goal
- Percentage-amount goal treated as amount goal
- No linked product treats raised as 0
- Negative raised clamps to 0
- Zero goal amount disables amount goal
- Per-campaign instance cache
- Cache reset returns fresh instance

## Backward compat

- All toggles default off.
- The two new wrapper attributes are additive: sites that haven't opted in see `data-fully-funded="0"` + empty `data-general-fund-url` + no behavior change.
- `Config_Resolver::get_global_settings()` returns the new keys with safe defaults via `Defaults::for_global()`; existing options upgrade transparently on next read.

## What this doesn't do

- Doesn't track donor pledges. "I'll fund the rest" promises are out of scope.
- Doesn't auto-disable the campaign on goal-met. Admins who want auto-archive can hook `dfwc_companion_donation_submitted` and check `Goal_State::is_fully_funded()`.
- Doesn't allocate overflow automatically. The donor's overflow decision is voluntary — they click the CTA.
