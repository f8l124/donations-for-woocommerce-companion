# v2.0.0 — QuickBooks Online Sync

Real-time per-donation Sales Receipt creation in QuickBooks Online. OAuth2 with admin-supplied app credentials; encrypted token storage; campaign-to-income-account mapping; async retry queue powered by Action Scheduler. Listens on the standard `dfwc_companion_donation_submitted` Phase 9 hook so cash + stock + (eventually) crypto donations all sync uniformly through the same pipeline.

Off by default. Existing v1.3.x sites see zero behavior change until admin opts in via *WooCommerce → Donations Companion → Settings → QuickBooks Online sync*.

## Why a major version bump

Two things land here that warrant `v1.x → v2.0.0` per the project's release-process doc:

- **First runtime third-party API surface.** Up through v1.3.0 the companion talked to its parent plugin and to itself. v2.0.0 adds outbound calls to Intuit's OAuth + REST endpoints — a meaningful expansion of the trust boundary.
- **Persistent encrypted-secret storage.** OAuth2 access + refresh tokens live encrypted in `wp_options`. Even with the careful threat model (see below), shipping a new persistent-secret surface is a major-version-worthy change.

## Why this exists

Bookkeepers running QBO want every donation as a Sales Receipt **automatically**. The manual flow (export CSV from WC, import to QBO) is brittle: forgotten exports, currency mismatches, donor-name typos, account-mapping drift. Real-time sync also surfaces revenue dashboards in QBO without waiting on a month-end batch. The companion does NOT replace QBO's reporting — it just makes sure every donation lands in QBO when the bookkeeper looks.

## Architecture

### Module layout

```
includes/QuickBooks/
├── Token_Store.php          encrypted persistence (AES-256-CBC; AUTH_KEY-derived)
├── OAuth_Client.php         Intuit OAuth2 (authorize / exchange / refresh / disconnect)
├── API_Client.php           QBO REST surface (3 endpoints; auto-refresh on 401)
├── Account_Mapper.php       campaign → income account mapping
├── Sync_Queue.php           Action Scheduler-backed queue + bounded log
├── Sync_Handler.php         worker; builds payload + handles retry/non-retry
└── Donation_Listener.php    bridges Phase 9 hook to the queue
```

Plus:

```
includes/REST/QBO_OAuth_Callback_Controller.php      OAuth landing endpoint
includes/Admin/QuickBooks_Page.php                   Connect / Disconnect / Mapping / Log UI
templates/quickbooks-page.php                        admin page template
```

### Listener path

```
donor submits donation (cash / stock / crypto)
        ↓
parent plugin / Stock_Pledge_Handler / TGB_Webhook_Handler
        ↓
do_action( 'dfwc_companion_donation_submitted', ... )
        ↓
QuickBooks\Donation_Listener
        ↓
Sync_Queue::enqueue( $job )            ← writes Action Scheduler row
        ↓
Action Scheduler invokes Sync_Handler::process( $job )    ← async, immediate
        ↓
API_Client::create_sales_receipt
        ↓
QBO Sales Receipt created
```

The donor-facing flow never blocks on QBO. Submit_Guard returns success the moment the donation lands; sync runs in the background.

### Why Action Scheduler

AS ships with WooCommerce core, so requiring it adds zero install friction (WC is already required). It guarantees execution even on traffic-starved sites (no need for a hit to `wp-cron.php`; AS hooks into shutdown). It provides admin UI + audit log for free at *Tools → Scheduled Actions*. Hand-rolling a queue would have meant duplicating those features.

### Why hand-rolled OAuth (no Intuit SDK)

The Intuit PHP SDK pulls in Guzzle + a heavy DI container. For our scope (4 REST calls + token refresh) it's overkill. `wp_remote_*` is sufficient and keeps the plugin SDK-free.

### Why per-admin Intuit app credentials (not shared)

Each admin registers their own app at developer.intuit.com and pastes the resulting client_id + client_secret. Three reasons over a shared-credential approach:

- The plugin maintainer (David) doesn't get tied to Intuit's app-review treadmill.
- No shared rate-limit pain across sites.
- No ToS entanglement when plugin users upload their own QBO data through credentials we control.

The setup flow has more friction than "click Connect" → docs cover the developer.intuit.com walk-through.

### Retry policy

Failures route through `Sync_Handler::is_retryable`:

| HTTP status / error | Retry? |
|---|---|
| 5xx server errors | yes |
| 408 / 429 (rate-limited) | yes |
| 401 (token expired) | API_Client auto-refreshes once + retries; second 401 → fail |
| 400-403, 404, 422 | no — payload problem; logged + admin notification |
| Network-layer (cURL timeout, DNS, etc.) | yes |

Backoff: 60s → 5m → 15m → giving up. After 3 retries the job is marked failed and surfaces in the admin sync log + the new `qbo_sync_health` diagnostic check.

### Idempotency tradeoff

QBO's create-sales-receipt endpoint has no built-in idempotency key. A 5xx → backoff retry that succeeds AFTER a prior duplicate-write would create two receipts. Bookkeeper's safety net: every receipt has a `PrivateNote` of the form `dfwc-companion campaign=<id> context=<ctx>`. A monthly query in QBO for `PrivateNote like 'dfwc-companion%'` plus a `TxnDate` group-by surfaces dupes for manual cleanup.

Acceptably rare for v2.0.0. Optional idempotency keys via QBO webhook reconciliation are roadmap for v2.1.

## Threat model

### Token storage (in scope)

An attacker who reads `wp_options` via SQLi, a leaked SQL backup, or a misconfigured backup-as-zip download must not get plaintext access tokens.

Implementation: AES-256-CBC, key derived from `AUTH_KEY . AUTH_SALT . 'dfwc-qbo-token-store'` via SHA-256. Per-write random IV prefixed onto ciphertext. Without `AUTH_KEY` the ciphertext is indistinguishable from random. Tested: two writes of identical plaintext produce different ciphertext (per-write IV randomness defeats backup-comparison "did this token rotate?" inference).

### Token storage (out of scope)

An attacker with full filesystem read can read `AUTH_KEY` from `wp-config.php` and decrypt. Defending against that requires a real KMS, which is out of scope for a self-hosted plugin. Recommendation if your deployment makes that threat real: use a third-party secrets manager and inject `AUTH_KEY` from there.

### OAuth callback CSRF

`OAuth_Client::authorize_url()` mints a 32-char random state nonce, stores it in a 10-minute transient keyed by the admin user ID, and includes it in the Intuit redirect URL. `OAuth_Client::consume_state()` verifies the state on callback and burns the transient (single-use). State mismatch → callback returns an error; no token exchanged.

### Refresh token exposure

Refresh tokens encrypted at rest. Disconnect calls Intuit's revoke endpoint to invalidate the refresh token server-side too — even if the local DB is later compromised, the leaked refresh token won't grant access tokens.

## Privacy posture

The sync surface follows the Phase 9 hook contract: aggregate-only data flows to QBO. The Sales Receipt payload contains:

- Campaign title (admin-supplied; no donor PII)
- Donation amount + currency
- Income account ID
- Transaction date
- Private note carrying campaign ID + context

The Sales Receipt does NOT include donor name, email, IP, address, or any other identifier. Admins who want named-customer receipts can layer that on via the `dfwc_companion_qbo_payload` filter.

## Diagnostics

`Donations Companion → Diagnostics` adds two checks:

- **`qbo_connection`** — silent pass when sync is off; warn when tokens missing, refresh-token within 10 days of expiry; pass otherwise (shows connected company name + days remaining).
- **`qbo_sync_health`** — silent pass when sync is off; warn when more than 5 failures in last 24h; pass otherwise.

CLI: `wp dfwc-companion health` includes both checks.

## CLI

```bash
# Re-enqueue donations from the last 30 days for ALL campaigns.
wp dfwc-companion qbo-sync

# Restrict to a single campaign + look back 90 days.
wp dfwc-companion qbo-sync --campaign=123 --days=90

# Preview without enqueueing.
wp dfwc-companion qbo-sync --dry-run
```

## Test coverage

241 → 268 cases, 621 → 683 assertions.

New suites:

- **`QBO_Token_Store_Test`** (10 cases) — round-trip encrypt/decrypt, ciphertext-vs-plaintext guarantee, IV randomness across two writes of the same plaintext, corrupt-blob fails closed (returns empty rather than throwing), preserve-refresh on access-only update, clear() wipes state.
- **`QBO_Account_Mapper_Test`** (8 cases) — per-campaign vs default fallback, empty-string strip, non-numeric reject, key normalization, clear-removes-all.
- **`QBO_Sync_Queue_Test`** (7 cases) — log appends with server timestamp, ring-buffer cap at 50, failures-since window correctly bounds by timestamp + status filter, AS-unavailable logs error rather than fatal.
- **`QBO_OAuth_State_Test`** (5 cases) — single-use state nonce (replay returns false), authorize_url empty when credentials missing, scope + response_type fields present in URL.

## Backward compat

- Phase 9 hook signature unchanged; existing listeners (FluentCRM tagger, GA4 sender, Overflow webhook handler, etc.) continue to work.
- The new admin submenu is conditional; sites that don't enable QBO sync see zero UI changes.
- No new DB tables — Action Scheduler reuses its own tables; we add three options (`dfwc_qbo_oauth_tokens`, `dfwc_qbo_account_mapping`, `dfwc_qbo_sync_log`).
- The existing Submit_Guard, Stock_Pledge_Handler, and Overflow webhook code paths fire the standard `donation_submitted` hook unchanged; sync wiring sits at the listener boundary.

## What this doesn't do (yet)

- **Refunds.** WC refunds don't flow to QBO; bookkeepers reconcile manually. Roadmap for v2.1.
- **Per-currency account mapping.** All currencies for a campaign route to one income account. Roadmap for v2.1.
- **Customer creation.** Receipts post as anonymous. Use the `dfwc_companion_qbo_payload` filter for named-customer flow.
- **Webhook reconciliation.** QBO supports webhooks; we don't subscribe. Could enable smarter idempotency in v2.1+.
- **Multi-realm.** One QBO realm per WP install. Sites that admin multiple orgs need one WP install per realm.
