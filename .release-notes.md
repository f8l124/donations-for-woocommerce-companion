# v2.3.0 — Crypto donations via The Giving Block

Third donor channel alongside cash (existing) and stock (v1.3.0). Donors complete the wallet handshake inside The Giving Block widget; companion records the order, fires the Phase 9 hook, and integrates with existing CRM/analytics listeners identically to cash donations.

The companion is the orchestration layer; The Giving Block is the only counterparty for blockchain interaction, KYC/AML, and supported-coin lifecycle. We never touch a wallet, never see a transaction hash, never call a blockchain RPC.

## What ships

### Donor side
- "Donate Crypto" button below the cash form on every crypto-enabled campaign.
- TGB widget lazy-loads on first click — never on page load, never on non-crypto campaigns.
- On donor commit: `on-hold` WC order created immediately (donor sees it in their account).
- Webhook fires when on-chain confirms (~5-30 minutes typically): order flips to `completed`, Phase 9 hook fires.

### Admin side
- New page: `WooCommerce → Donations Companion → Crypto Donations`. Sandbox/production toggle, organization id, encrypted API key + webhook secret, default project routing, Test connection / Refresh project list / Disconnect actions.
- New side meta box on every campaign edit screen: "Crypto donations" (only visible when global crypto is on + connected). Per-campaign opt-out + project routing dropdown.
- Two new diagnostic checks: TGB connection health + webhook activity proxy (warns on the combination of "stale on-hold orders" + "no recent webhooks").

### Architecture
- 5 new gateway classes: `TGB_Token_Store` (encrypted credential storage), `TGB_Client` (REST client with sandbox/prod env switching), `TGB_Pending_Order` (order creation + idempotency), `TGB_Webhook_Handler` (HMAC verify + status transitions), `TGB_Project_Mapper` (campaign → project resolution + reverse-lookup), `TGB_Projects_Cache` (transient-cached project list), `TGB_Payment_Gateway` (custom WC `dfwc_crypto` method).
- 2 new REST controllers: `Crypto_Pending_Order_REST_Controller`, `TGB_Webhook_REST_Controller`.
- 1 new server-side renderer: `Crypto_Donation_Renderer`.
- 1 new client-side module: `assets/js/dfwc-crypto.js` (self-contained; same MutationObserver + WeakSet idempotency + popup-clone pattern as v2.2.4 overlay).

### Internal
- Test coverage 252 → 374 PHPUnit cases (+122). Six new unit-test files cover: encryption round-trip, HTTP error handling, gating decisions, payload sanitization, HMAC verification (correct + wrong secret + wrong body + empty edge cases), JSON parsing + event allow-listing, project resolution + namespace isolation.

## Phase 9 hook contract preserved

```php
add_action(
    'dfwc_companion_donation_submitted',
    function ( $campaign_id, $interval, $amount, $context, $currency, $language, $reason ) {
        if ( 'crypto' === $context ) {
            // Crypto-specific handling.
            // $amount is USD (TGB's reporting unit).
            // Original coin + crypto-amount available via order line-item meta.
        }
    },
    10,
    7
);
```

For crypto: `$interval = 'one_time'` (recurring deferred to v2.3.1+), `$context = 'crypto'`, `$currency = 'USD'`, `$language = ''`, `$reason = ''`.

## Race-safe + idempotent

- Pending-order REST creates `on-hold` order tied to the TGB donation_id.
- Webhook flips status to `completed` and fires Phase 9 hook.
- If the webhook arrives BEFORE the pending-order POST (rare; slow client): webhook handler creates the order from the webhook payload and flips immediately. The deferred POST sees the existing order via `find_existing_by_donation_id` and returns 200 idempotent.
- If the webhook arrives twice (TGB retry): second call sees `completed` status and no-ops. Phase 9 hook fires exactly once per donation_id.

## Security

- API key + webhook secret encrypted at rest (AES-256-CBC with key derived from `AUTH_KEY . AUTH_SALT`). Stored in a separate option from the public global settings so secrets never live alongside form-rendered fields. Never re-displayed to admin after save — admins rotate by re-entering.
- Webhook HMAC-SHA256 verification with `hash_equals` constant-time compare.
- Webhook endpoint feature-gated (404 when crypto disabled — URL scrapers can't fingerprint the endpoint exists).
- Rate-limited (60 req/min/IP for webhooks, 10 req/min/IP for pending-order POST).
- Body size cap (64KB on webhooks; TGB payloads are <2KB).
- Custom `dfwc_crypto` payment method `is_available()` returns false unconditionally — defense in depth even if an admin enables the gateway in WC settings.

## Documented constraints

1. **One-time crypto only.** Recurring deferred to v2.3.1+ — TGB supports it for limited coins, donor-side authorization UX is murky.
2. **USD denomination.** Orders are denominated USD regardless of WC store base currency (TGB's reporting unit). Cross-currency reconciliation is a v2.3.x concern.
3. **No refund flow.** TGB-side refunds require manual coordination via TGB's dashboard.
4. **No native KYC.** TGB handles donor identity verification above their threshold ($5,000+ as of writing).
5. **No on-chain interaction.** Companion is the orchestration layer; TGB is the sole blockchain counterparty.
6. **Single TGB org per site.** Multi-org agencies need separate WP installs at v2.3.0.

## Channel-extension API note

v2.3.0 ships the third donor channel (cash + stock + crypto). The internal pattern — channel-specific renderer + REST controller(s) + admin section + Phase 9 fire with channel-specific `$context` — becomes the formal `Donor_Channel` interface in v3.0.0 (per `plans/v2/v3-channel-api-and-extraction.md`). v3.0.0 also enables the GiveSpring extraction (`plans/givespring/spec.md`) — companion's parent-coupled code partitions cleanly into the `ParentBridge\*` namespace, and the rest of the codebase forks portably.

## Backward compat

Sites without crypto: zero behavior change. The donor form is unchanged. The crypto JS module ships unconditionally but early-returns on `data-crypto-enabled="0"` — the cost on non-crypto pages is a small inert script parse.

Sites with prior companion versions: no data migration. The new global settings + per-campaign overrides are additive.

Sites that previously used the now-extracted QBO sync (v2.0.x): unaffected — QBO is in the sibling plugin since v2.1.0; crypto is independent.

Major-version bump rationale: NOT bumped to 3.x because (a) no public PHP API breakage, (b) no class autoload path changes, (c) no stored data migration, (d) opt-in feature with zero default-on impact. v3.0.0 is reserved for the channel-extension API refactor (per the v3 plan); v2.3.0 is a focused minor that adds the third channel within the existing architecture.
