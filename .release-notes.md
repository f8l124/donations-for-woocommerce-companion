# v2.2.2 — Drag-drop preset reorder bug fix

User-reported bug: in the campaign meta box, dragging preset amounts (most visibly 25, 50, 100 — the defaults) into a new order *appeared* to work — the visual order updated, the form submitted, the success notice fired — but on next render the defaults sank back to the bottom of the list, undoing the reorder.

## Root cause

`renumberRows()` in `assets/js/dfwc-admin.js` is responsible for rewriting input attributes after a drag-drop reorder. It correctly rewrote:

- The array index in each input's `name` attribute (`name="dfwc_intervals[monthly][presets][0][amount]"` → `[presets][1][amount]` to reflect the new DOM position).
- The per-row default radio's `value` attribute so the server-side `default_index` matched a real row after reorder.

But it **skipped** the per-row hidden `sort_order` input's `value` attribute. Each preset row carries a hidden `sort_order` (initially 10, 20, 30, etc.) that the server uses as the source-of-truth ordering on render. After a drag-drop:

- Visual order: 100 → 25 → 50.
- DOM input names rewritten: `[presets][0]` is now the row containing 100, etc. ✓
- But `[presets][0][sort_order]` hidden value still says `30`. ✗

Save flow:

```
$_POST['dfwc_intervals']['monthly']['presets'] = [
  0 => ['amount' => 100, 'sort_order' => 30],   // moved to top visually, but sort_order still 30
  1 => ['amount' => 25,  'sort_order' => 10],
  2 => ['amount' => 50,  'sort_order' => 20],
]
```

Save handler stores those values verbatim. Next render, `Config_Resolver::validate_and_clamp()` sorts presets ASC by `sort_order` — and 10 < 20 < 30 reasserts the original order. From the admin's perspective: defaults always sink to the bottom.

## Fix

One-block addition in `renumberRows()`:

```js
if ( input.type === 'hidden' && input.name && input.name.indexOf( '[sort_order]' ) !== -1 ) {
    input.value = String( ( idx + 1 ) * 10 );
}
```

Now after every reorder the hidden `sort_order` values are rewritten to `10, 20, 30, ...` matching the visual order. The save persists what the admin sees.

## Recovery for stuck campaigns

If a campaign currently has out-of-order presets due to this bug:

1. Upgrade to v2.2.2.
2. Edit the campaign.
3. Drag any preset row, drop it (you can drag-and-drop in place — the act of triggering `dragend` is what runs `renumberRows()`).
4. Save Campaign.

The save now rewrites all `sort_order` values to match the visual order, and the new order sticks.

## Backward compat

- No data migration. Existing stored `sort_order` values respected by the resolver as before.
- Old admin sessions still in the page (browser cached the old JS) keep buggy behavior until cache reload — soft refresh or clear LiteSpeed Cache after upgrade.
- Campaigns that don't use drag-drop (admin types presets directly) were never affected.

## Why this took until v2.2.2 to surface

The bug existed since drag-drop reorder was added (Phase 5, v0.9.0+). It only manifests when admins reorder presets that have `sort_order` values different from `(idx+1)*10` at the time of drag — which is the default state for fresh campaigns. Admins often add presets after the defaults; those new ones get sort_order from the renumber path and reorder works fine. The "default 25/50/100 reorders are broken" pattern surfaces specifically when an admin tries to reorder the defaults themselves.

Patch-level bump (v2.2.1 → v2.2.2). User-facing bug fix; no behavior change beyond making drag-drop work as expected.
