# v2.2.4 — Donor form in modal popups (Elementor Pro / generic) now interactive

User-reported bug: dropping the companion's "Recurring Donation" Elementor widget into an Elementor Pro popup template rendered the form correctly — tabs, preset cards, donate button all visible — but **none of the controls responded to clicks**.

## Root cause

`assets/js/dfwc-overlay.js` ran a single `DOMContentLoaded` scan:

```js
ready( function () {
    var targets = document.querySelectorAll( '[data-dfwc-overlay-target]' );
    Array.prototype.forEach.call( targets, init );
} );
```

`init()` builds the tabs UI dynamically and binds click handlers to each tab button via `addEventListener`. That works fine for forms rendered inline on a page.

When Elementor Pro shows a popup, it **clones** the popup template's DOM into a visible container. `addEventListener` listeners are NOT preserved on cloned nodes — only attribute-based handlers (`onclick="..."`) survive cloning. So:

- The visible tabs the donor sees are **clones** of the originals, with no bound handlers.
- The originals (in Elementor's offscreen template store) still have handlers, but the donor never sees them.
- Tabs render, are styled correctly, but click does nothing.

Same root cause meant preset cards and the submit button were also dead.

## Fix

Four-part change in [dfwc-overlay.js](assets/js/dfwc-overlay.js):

### 1. MutationObserver on `document.body`

```js
function startObserver() {
    if ( typeof MutationObserver !== 'function' || ! document.body ) { return; }
    var observer = new MutationObserver( function ( mutations ) {
        for ( var i = 0; i < mutations.length; i++ ) {
            var added = mutations[ i ].addedNodes;
            for ( var j = 0; j < added.length; j++ ) {
                var node = added[ j ];
                if ( ! node || node.nodeType !== 1 ) { continue; }
                var isWrapper = node.matches && node.matches( '[data-dfwc-overlay-target]' );
                var hasWrapper = node.querySelector && node.querySelector( '[data-dfwc-overlay-target]' );
                if ( isWrapper || hasWrapper ) {
                    initAll();
                    return;
                }
            }
        }
    } );
    observer.observe( document.body, { childList: true, subtree: true } );
}
```

Detects when a new `[data-dfwc-overlay-target]` wrapper is added to the DOM — by any popup builder, modal library, or AJAX-injected campaign embed — and re-runs `initAll()` on it. Generic across popup ecosystems, not Elementor-specific.

### 2. Elementor `popup/show` listener (belt-and-suspenders)

```js
document.addEventListener( 'elementor/popup/show', function () {
    setTimeout( initAll, 0 );
} );
```

Some popup builders recycle offscreen DOM via a class-flip rather than appending a fresh subtree — MutationObserver `childList` wouldn't catch that. Elementor's documented popup-show event covers the gap. The `setTimeout(0)` lets Elementor finish its own DOM tweaks before our re-init runs.

### 3. WeakSet idempotency guard

```js
var initializedWrappers = ( typeof WeakSet === 'function' ) ? new WeakSet() : null;

function init( wrapper ) {
    if ( initializedWrappers && initializedWrappers.has( wrapper ) ) { return; }
    // ... existing init logic ...
    if ( initializedWrappers ) { initializedWrappers.add( wrapper ); }
}
```

Re-running init on a wrapper we've already booted is a no-op. Cloned wrappers are *different DOM nodes* (different element references), so they bypass this guard naturally and get a fresh init pass — no double-binding the original.

### 4. Stale-clone cleanup at init start

When Elementor clones the popup template into the visible container, the clone already carries our overlay UI (`.dfwc-overlay__root`, `.dfwc-overlay__goal-met`, `.dfwc-overlay__stock-pledge`) from the original init pass. If we naively re-init on the clone, we'd insert a *second* overlay UI alongside the stale clone.

```js
if ( scope ) {
    var staleNodes = scope.querySelectorAll( '.dfwc-overlay__root, .dfwc-overlay__goal-met, .dfwc-overlay__stock-pledge' );
    for ( var s = 0; s < staleNodes.length; s++ ) {
        if ( staleNodes[ s ].parentNode ) {
            staleNodes[ s ].parentNode.removeChild( staleNodes[ s ] );
        }
    }
}
```

Clean rebuild every time. Parent's hidden `.row1` blocks (which were `display:none`-set by the original init) survive cloning with the inline style intact, so we don't need to re-hide them.

## Compatibility surface

This bug class wasn't Elementor-specific. Any modal library that clones DOM at show-time would have hit it: Popup Maker (some configurations), Beaver Themer, custom Bootstrap modals loading content via AJAX, Divi popups, and so on. The fix covers the whole class.

## Side benefit — admin live preview pane

The Phase 8 live admin preview iframe re-renders the donor form on debounced input changes (every 350ms when admin types). Pre-v2.2.4, those re-renders relied on iframe reload to trigger a fresh DOMContentLoaded. Post-v2.2.4, the MutationObserver + idempotency guard mean re-renders that swap the wrapper subtree (rather than fully reloading the iframe) also re-init correctly. Not exercised by current preview UX, but unblocks future preview optimizations.

## Test coverage

252 → 252 PHPUnit (no PHP changes). The fix is in client-side JS exercised by manual QA + Playwright E2E (admin preview pane scenario). A targeted Playwright spec for "form inside Elementor popup" would be valuable but requires a fixture site with Elementor Pro — deferred.

## Backward compat

- Sites without popups: zero behavior change. Initial `DOMContentLoaded` scan path identical to v2.2.3. The MutationObserver fires for every body subtree mutation but exits cheaply when no overlay wrapper is involved.
- Sites with the form inline on a page (shortcode / block / Elementor widget on a regular page): zero behavior change. Init runs once on DOMContentLoaded, WeakSet records the wrapper, no re-init triggered.
- Sites already using popups but where it happened to work (e.g., a popup builder that doesn't clone): zero behavior change beyond a tiny MutationObserver overhead.

## Cache invalidation

The companion's JS enqueue uses `DFWC_COMPANION_VERSION` as the version string for `wp_enqueue_script`, so the URL changes from `dfwc-overlay.js?ver=2.2.3` to `?ver=2.2.4` — browsers fetch fresh. Sites with aggressive page caching (LiteSpeed, WP Rocket, full-page caches) should purge after upgrade so the new asset URL gets into rendered HTML.

## Why this took until v2.2.4 to surface

The companion's primary embed paths (shortcode in post body, Gutenberg block, Elementor widget on a regular page) all render inline at page load time and never trigger DOM cloning. Popups are a less-common embed pattern and only fail under cloning popup builders. The user hit this when explicitly trying the "donate from a button in a popup" pattern — a perfectly reasonable nonprofit-site UX that wasn't on the original test matrix.

Patch-level bump (v2.2.3 → v2.2.4). Pure JS bug fix; no data migration; donor flow uninterrupted on inline embeds.
