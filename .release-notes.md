# v1.3.0 — Stock Donations

Two opt-in modes for accepting donations of appreciated securities, picked per-site by the admin:

1. **Built-in pledge form** — donors fill an inline form on your campaign page; companion captures the pledge, emails them your DTC transfer instructions, and tracks the pledge through to receipt.
2. **Overflow integration** — donors click through to your hosted [Overflow](https://overflow.co/) page where the entire transfer is automated; Overflow notifies the companion via webhook when the donation completes.

Both off by default. Existing v1.2.x sites see zero behavior change until admin opts in via *WooCommerce → Donations Companion → Settings → Stock donations*.

Crypto donations are NOT in this release — they ship in v1.4.0 via The Giving Block integration. Pragmatic scope: stock alone is sizeable, and the user-facing flow + reconciliation surface are best validated in production before stacking another non-cash channel.

## Why this exists

Stock gifts are a major giving channel for nonprofits — Bridgespan estimates ~70% of donor wealth in the U.S. is in non-cash assets. The donor flow is process-not-instant: the donor *pledges* the gift, then their broker transfers shares to the org's brokerage, which can take days or weeks. The companion's role is to capture the pledge cleanly, give the donor what they need to forward to their broker, and track the pledge through to receipt — at which point the standard `dfwc_companion_donation_submitted` hook fires (with `$context = 'stock'`) so QBO sync (Phase 15+), CRM listeners, GA4 events, etc. all see stock donations as first-class donations alongside cash.

Two modes exist because two distinct operational models do:

- **Pledge form mode** is right for orgs with their own brokerage account that want zero per-transaction fees and stock gifts to flow through their own infrastructure.
- **Overflow mode** is right for orgs that want a managed flow with KYC, tax-receipt generation, and broker-side automation handled by a SaaS provider.

## Architecture

### Pledge custom post type

`dfwc_stock_pledge` — admin-only CPT. Each pledge is a discrete record with status tracked in the `_dfwc_stock_pledge_status` meta key (NOT the WP `post_status`, which stays `publish` throughout — meta-driven workflow keeps standard WP_Query usable).

```
pledged → in_transit → received  (terminal)
              ↘
               cancelled
```

14 meta keys for donor info, broker info, stock details, status, admin notes, plus `_dfwc_stock_pledge_overflow_id` for mode-2 idempotency.

### `Stock_Pledge_Handler`

Centralized create / mark-received / transition-status / read-pledge surface. Donor input is sanitized via allow-list rules:

- Ticker regex `^[A-Z]{1,5}(\.[A-Z]{1,2})?$` — covers most U.S. equity symbols including class shares (BRK.B). Rejects digits, foreign tickers.
- Shares ∈ (0, 1,000,000].
- Estimated value ∈ (0, $100,000,000].
- Donor notes capped at 2000 chars, sanitized via `sanitize_textarea_field`.
- `campaign_id` must reference a `wc-donation` post.

PII never flows raw through Phase 9 hooks: `dfwc_companion_stock_pledge_created` receives `sha256(strtolower(trim($email)))`; the standard `dfwc_companion_donation_submitted` hook carries only aggregate data.

### Donor-side flow (mode 1)

`POST /wp-json/dfwc-companion/v1/stock-pledge` — public REST endpoint:

- Permission callback `__return_true` (no auth — donors are anonymous).
- Rate-limited 5 requests/IP/min via `dfwc_rate_limit_*` transients (hashed-IP keys).
- Returns 404 (NOT 403) when the feature is disabled so misconfigured donor-side JS doesn't trip security scanners.
- Returns DTC instructions in the success response so the donor sees confirmation immediately.

The overlay JS (`assets/js/dfwc-overlay.js`) reads three new wrapper attributes:

```html
<div data-dfwc-overlay-target
     data-stock-pledge-enabled="1"
     data-stock-mode="pledge_form"
     data-stock-overflow-url=""
     ...>
```

When mode = `pledge_form`, `mountStockPledgePanel` renders an inline form. When mode = `overflow`, `mountStockOverflowButton` renders a single anchor link with `?utm_source=dfwc-companion&campaign_id=N` appended via the URL API.

### Webhook (mode 2)

`POST /wp-json/dfwc-companion/v1/overflow-webhook`:

- HMAC-SHA256 verification using the admin-configured secret + `hash_equals` for constant-time comparison.
- Rejects unsigned payloads with HTTP 403.
- Idempotent: stores Overflow's external donation ID in `_dfwc_stock_pledge_overflow_id` post meta; replays of the same webhook are recognized and no-op'd.
- Permissive about Overflow's exact field names (`transaction_id` || `donation_id` || `id`) since their payload shape has shifted between versions.
- 404 (not 403) when stock donations are toggled off so Overflow's retry logic backs off cleanly.

On verified webhook, creates a `received`-status pledge record AND fires `dfwc_companion_donation_submitted` immediately — Overflow webhooks arrive only after the share transfer completes, so no admin reconciliation step needed.

### Phase 9 hook integration

Two hooks fire:

- `dfwc_companion_stock_pledge_created` ($pledge_id, $campaign_id, $hashed_email) — pledge-form mode only, fires on donor submit. Use for CRM "pending pledge" entries, Slack notifications.
- `dfwc_companion_donation_submitted` (same signature as cash donations, with `$context = 'stock'`) — fires when admin runs **Mark received** in pledge-form mode, or when an Overflow webhook arrives in overflow mode. Identical shape to cash submit hook, so existing listeners pick stock up without code changes.

Listeners that want to *exclude* stock donations from their flow check `if ('stock' === $context) { return; }`.

### Wrapper-attribute parity (cerebrum reminder)

The three new attributes are emitted at all three wrapper sites: `Renderer::wrap_with_overlay`, `Context_Augmenter::emit_open`, `Preview_Renderer::render`. The Do-Not-Repeat from the v1.0.0 release reminded that drift between these emit sites manifests as preview-vs-donor mismatches; this release keeps them in sync.

## Admin UI

`WooCommerce → Donations Companion → Settings → Stock donations` — 9 settings:

| Field | Mode | Default | Behavior |
|---|---|---|---|
| Enable stock donations | both | off | Master toggle |
| Mode | both | pledge_form | Dropdown: pledge_form OR overflow |
| Brokerage name | mode 1 | — | Appears in donor confirmation email |
| DTC account number | mode 1 | — | Appears in donor confirmation email |
| DTC clearing house number | mode 1 | — | Appears in donor confirmation email |
| Org tax ID (EIN) | mode 1 | — | Appears in donor confirmation as receipt context |
| Admin notification email | mode 1 | — | Where pledge alerts go (defaults to WP admin email) |
| Overflow URL | mode 2 | — | Public URL of the Overflow donation page |
| Webhook secret | mode 2 | — | HMAC signing secret; redacted in admin UI on save |

`WooCommerce → Donations Companion → Stock Pledges` is a new admin page (conditional submenu — only registered when stock donations are enabled). Provides:

- Subsubsub status filter (All / Pledged / In transit / Received / Cancelled)
- Full pledge data on the edit screen
- Two reconciliation forms:
  - **Mark received** — primary path; enter actual transfer value + date, fires Phase 9 hook
  - **Update status** — for transitional bookkeeping (in_transit / cancelled); doesn't fire the donation hook

## Privacy posture

Stock donations carry more donor PII than cash (broker name, full donor name, phone) because the operational flow requires it — your team needs to reach the donor's broker if shares get stuck. The companion's posture:

- Donor PII lives in WP post meta on the `dfwc_stock_pledge` CPT, accessible only to admins with `manage_options`.
- Phase 9 `dfwc_companion_stock_pledge_created` receives sha256-hashed email, never raw.
- Phase 9 `dfwc_companion_donation_submitted` carries `context='stock'` and amount, no donor identifiers.
- Overflow mode: donor PII lives in Overflow's system; companion stores only the external donation ID + amount + currency.

## Backward compat

- Existing v1.2.x campaigns render unchanged.
- The three new wrapper attributes are additive: sites without stock donations enabled emit `data-stock-pledge-enabled="0"` and the donor-side panel never mounts.
- No new tables; `dfwc_stock_pledge` CPT is admin-only and irrelevant on sites that haven't enabled the feature.
- `uninstall.php` extends to wipe `dfwc_stock_pledge` posts when *Preserve data on uninstall* is off.

## What this doesn't do

- Doesn't generate IRS tax receipts. Pledge data feeds your existing receipt flow; the receipt template itself is your responsibility.
- Doesn't talk to broker APIs directly. Direct broker integrations are a multi-broker compliance surface that's out of scope.
- Doesn't auto-mark pledges received. In mode 1 the admin is the source of truth on share arrival; auto-detection would require live brokerage API access.
- Doesn't track donor cost basis. IRS rules say stock-gift receipts use FMV at transfer date; the donor's cost basis is the donor's tax-prep concern.
- Doesn't accept crypto. That's v1.4.0.
