# v2.4.0 — Cause-aware giving

Per-cause goals + 3-mode closure UX. Extends v1.2.0 goal-aware giving (which operated at the campaign level) down to the cause level. Admins set per-cause goals; companion tracks per-cause raised totals from existing WC order data and closes causes when their goal is reached.

## What ships

### Donor side

A donor visiting a campaign with cause-goal tracking enabled sees:
- The standard cause picker with one or more causes that have hit their goals **either** silently hidden, OR shown reduced-opacity with click handlers that surface alternatives, OR shown reduced-opacity with click handlers that redirect to a general fund — depending on the configured closure mode.
- A yellow inline "Education reached its goal!" card with buttons for each open alternative (Mode B, default). Click an alternative → it auto-selects.
- Server-side enforcement: closed causes reject submits even when the donor bypasses client UI via DevTools or curl. Mode-aware error messages.

### Admin side

- New per-campaign meta box "Per-cause goals" (visible when global cause goals is on). Track checkbox + Goal amount + Closure mode dropdown per cause. Inherit option label dynamically shows the resolved global default.
- Two new global settings under "Goal-aware giving": Enable per-cause goals + Default cause closure mode.
- One new diagnostic check (cause_goals_health) flags orphaned config (goals set but parent's cause picker disabled).
- New `dfwc_companion_cause_closed` extension hook fires once when a cause's raised total crosses its goal — admins can cancel matching subscriptions, post to Slack, etc.

### Architecture

- Stable cause IDs (companion-minted UUIDs threaded through cart → order line items). Renames in parent's UI preserve historical order attribution.
- 3-layer cache: per-request memo (closure renderer hits each cause many times per render) + 5-minute transient + single SQL aggregate. HPOS-aware (branches on OrderUtil for the orders-table JOIN).
- Cart-hook + order-item-hook (priority 20, after parent's adds at priority 10) thread our cause-id through the standard WC flow.
- Closure decision composite (`Cause_Closure_Service`) consulted by both server-side Submit_Guard AND client-side overlay JS — single source of truth.

## Recurring exemption (deliberate design)

Closure blocks NEW donations only. Existing sustainers whose monthly schedule was set up before the cause closed continue to renew normally. Two reasons:

1. **WC subscription pipeline bypass.** WCS / WPS SFW route renewals through their own pipeline — they don't hit parent's `donation_to_order` AJAX action. Submit_Guard's closure check only runs in that AJAX action. The "renewals exempt" guarantee upholds itself by virtue of the action-surface boundary.
2. **Donor trust.** Auto-cancelling a sustainer's recurring gift because the cause they originally chose is now fully funded is a hostile UX — the donor's intent ("monthly support to this org") is broader than their cause selection. We don't violate it.

Admins who want different policy (e.g., notify donors that their cause closed and offer to redirect their recurring) can listen on `dfwc_companion_cause_closed` and act explicitly.

## HPOS aware

The aggregator's SQL JOIN branches on `OrderUtil::custom_orders_table_usage_is_enabled` (when that class exists — WC 7.1+ ships it). HPOS sites JOIN against `wp_wc_orders`; legacy sites JOIN against `wp_posts` filtered by `post_type = 'shop_order'`. Line-item meta storage is unchanged across the migration, so the bulk of the SQL is shared.

## Documented constraints

1. **No backfill of legacy orders.** Pre-v2.4.0 orders don't carry our `_dfwc_companion_cause_id` line-item meta; raised totals fall back to name-match for those orders. Documented degraded behavior.
2. **Refunds NOT subtracted from raised totals.** Matches parent's own raised-tally semantics. v2.5+ candidate.
3. **Cross-currency cause goals.** Goals denominated in WC base currency. v2.5+ enhancement.
4. **No per-cause progress bars on the donor form.** v2.5+ candidate; needs UX design.
5. **HTML entities in cause names.** Stick to plain text in cause names — parent's storage doesn't escape, donor-side selector matching may fail otherwise.

## Backward compat

Sites without cause goals: zero behavior change. The donor form is unchanged. The `data-closed-causes` attribute ships as `{}` on campaigns with no closed causes — cheapest possible signal for the donor JS to skip its closure-rendering pass.

Sites already running prior companion versions: no data migration. Per-cause goals are a new override namespace; existing intervals/display/crypto overrides are untouched.

## Architectural note — v3.0.0 readiness

v2.4.0 ships the second feature using the channel-pattern (storage + admin + Phase 9 fire) established in v2.3.0 crypto. Both features have similar structural shapes — config service, schema, admin meta box section, server-side trust boundary, donor-side renderer/JS extension. v3.0.0 will refactor these into the formal `Donor_Channel` interface (per `plans/v2/v3-channel-api-and-extraction.md`), which also enables the GiveSpring extraction.

Major-version bump rationale: NOT bumped to 3.x because (a) no public PHP API breakage, (b) no class autoload path changes, (c) no stored data migration, (d) opt-in feature with zero default-on impact. v3.0.0 is reserved for the channel-extension API refactor; v2.4.0 is a focused minor.
