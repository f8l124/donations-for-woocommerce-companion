# v2.2.3 — Upgrade-via-Delete data-loss hotfix

User-reported bug: campaign settings (intervals, presets, monthly/annual toggles, min/max, CTA template, display options) reverted to defaults every time the admin upgraded the plugin.

The trigger was the upgrade method, not the save flow. The admin was upgrading via **Plugins → Delete (old version) → Add New → Upload + Activate (new version)**. Deleting any WordPress plugin runs its `uninstall.php` — and ours was wiping per-campaign post meta on installs where the *Preserve data on uninstall* checkbox had never been explicitly toggled.

## Root cause

`uninstall.php` line 21:

```php
$dfwc_global   = get_option( 'dfwc_companion_global_settings', array() );
$dfwc_preserve = is_array( $dfwc_global ) ? ! empty( $dfwc_global['preserve_data_on_uninstall'] ) : true;
```

The intent: default to preserve = `true`. The fall-through (`: true`) only fires when `dfwc_companion_global_settings` doesn't exist as an option at all. The moment the admin saves Settings (for any reason) the option exists as an array — and if `preserve_data_on_uninstall` isn't in that array, `! empty( $array['missing_key'] )` returns `false`, so preserve becomes `false` and uninstall wipes:

- `_dfwc_companion_intervals`
- `_dfwc_companion_display`
- `_dfwc_companion_template_id`
- `_dfwc_companion_overrides`
- `_dfwc_companion_detached`
- `_dfwc_companion_featured`

…from every post in the database via `delete_metadata( 'post', 0, $key, '', true )`. Then the new version installs, finds no overrides, and resolver returns defaults. The admin sees "campaign settings reset every time I upgrade".

`Defaults::for_global()` correctly declares `'preserve_data_on_uninstall' => true`. The form (`render_preserve_uninstall_field` line 248) correctly defaults to checked via `?? true`. The bug was specifically in `uninstall.php`, which reads the raw stored option without merging defaults — that's the only path that hits the missing-key fallback.

## Fix

`uninstall.php` now uses `array_key_exists` to distinguish "key missing from stored array" (admin never explicitly opted in to wipe) from "key explicitly set to false" (admin explicitly opted in):

```php
if ( is_array( $dfwc_global ) && array_key_exists( 'preserve_data_on_uninstall', $dfwc_global ) ) {
    $dfwc_preserve = ! empty( $dfwc_global['preserve_data_on_uninstall'] );
} else {
    $dfwc_preserve = true;
}
```

Result: a destructive uninstall only happens when the admin has *explicitly unchecked* the *Preserve data on uninstall* checkbox AND saved the Settings form. Every other path — option missing, option exists with key missing, option exists with key set to true — preserves data.

## Recovery

Already-wiped data from prior upgrades is unrecoverable from this fix alone. `uninstall.php` already ran in those prior upgrade cycles; the post meta is gone. Admins who upgraded via Delete + Upload before v2.2.3 need to reconfigure affected campaigns once. After this release, the next Delete + Upload cycle no longer poses the risk.

## Documentation

`readme.txt` gains a new `= Upgrading =` subsection under Installation:

> **Use the in-place upgrade path, not Delete + Upload.** When a new version is released:
>
> - Recommended: **Plugins → Add New → Upload Plugin →** drag the new ZIP → WordPress prompts *"This plugin is already installed"* → click **Replace current with uploaded** → activate. This preserves all campaign settings + templates + global config.
> - Avoid: **Plugins → Delete → Add New → Upload**. Deleting any WordPress plugin runs its `uninstall.php`. v2.2.3+ defaults to preserving data when the setting is missing or never explicitly turned off, but the in-place replace is still the safer path.
> - Auto-update via WordPress → Plugins is also safe (it runs the WordPress upgrader, not the uninstaller).

## Test coverage

251 → 251 cases. The bug lives in WordPress's plugin lifecycle (uninstall.php is invoked by WP, not by our boot path), so the fix is verified by code review + manual delete/upload cycle on a test site, not via PHPUnit.

## Backward compat

- Sites with `preserve_data_on_uninstall` explicitly set to `true` in the stored option: identical behavior (preserve).
- Sites with `preserve_data_on_uninstall` explicitly set to `false` in the stored option: identical behavior (wipe — admin opted in).
- Sites where the key is missing from the stored option: behavior changes from wipe to preserve. This matches the documented default and the form's default state.
- Sites with the option entirely missing (never opened Settings): no behavior change (already preserved via the `: true` branch).

## Why this took until v2.2.3 to surface

The bug existed since `preserve_data_on_uninstall` was added (v2.0.7). Most admins never encountered it because:

- Upgrades via WordPress's auto-updater don't run `uninstall.php`.
- Upgrades via "Replace current with uploaded" don't run `uninstall.php`.
- Only manual Delete + Upload triggers the bug, and only when the admin had previously saved Settings without that checkbox being explicitly checked.

This particular admin always upgraded via Delete + Upload (a habit predating WordPress's safer in-place upgrade UX), saw the symptom on every release, and reported it after v2.2.2. The fix is conservative — only the missing-key path changes behavior — so admins who explicitly opted into a clean uninstall keep that behavior.

Patch-level bump (v2.2.2 → v2.2.3). Critical bug fix; flips a destructive default that should never have been destructive.
