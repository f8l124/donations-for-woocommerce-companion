# v1.1.0 — Event Hooks

Adds six WordPress action hooks at key points in the donor flow so admins can pipe events to whatever analytics / CRM / webhook tool they already use. The companion deliberately ships **no** dashboard, no storage layer, and no third-party SDK — surfacing well-documented hooks and three end-to-end integration recipes is higher leverage than reinventing analytics for the ~95% of nonprofits already paying for one.

## What ships

| Hook | Fires when | Args |
|---|---|---|
| `dfwc_companion_form_viewed` | Donor sees the form | `$campaign_id, $context, $language` |
| `dfwc_companion_interval_selected` | Donor changes the active tab | `$campaign_id, $interval, $context, $language` |
| `dfwc_companion_preset_selected` | Donor clicks a preset | `$campaign_id, $interval, $amount, $context, $currency, $language` |
| `dfwc_companion_custom_amount_entered` | Donor types in custom-amount (after blur) | `$campaign_id, $interval, $amount, $context, $currency, $language` |
| `dfwc_companion_donation_submitted` | Server-side success after parent's AJAX | `$campaign_id, $interval, $amount, $context, $currency, $language, $reason` |
| `dfwc_companion_donation_failed` | Server-side failure | `$campaign_id, $interval, $amount, $context, $currency, $language, $reason` |

The first four are donor-side JS events that batch to a public, rate-limited `track` REST endpoint. The last two fire directly in PHP at the form-submit boundary via the parent's `wc_donation_alter_donate_response` filter. Signatures are stable through v1.x.

## Privacy posture

Every event passes through `Analytics\Privacy_Guard::sanitize_event` before any `do_action` fires. The Guard:

- Allow-lists event types, intervals, render contexts, currency codes, and language codes
- Replaces client-supplied timestamps with server time
- Caps amounts and reason strings to defeat overflow / log-injection
- **Silently drops PII fields** (donor_email, ip, user_agent, session_id, etc.) — even if a malicious client POSTs them

Listeners that need PII pull it from their own source (e.g. `WC()->customer->get_email()`). The hooks are aggregate-only by design.

## Defenses

| Layer | Limit |
|---|---|
| Batch size cap | 50 events per request |
| Rate limit | 100 events / IP / minute (hashed-IP keys, transient-backed) |
| Allow-list | Every event field validated against an explicit set |
| Server time | Client-supplied `ts` ignored |

## Three integration recipes

`docs/event-hooks.md` ships with copy-paste-ready snippets for:

1. **Google Analytics 4** via the Measurement Protocol — server-to-server, no client tag, ~10s end-to-end
2. **FluentCRM** contact tagging — auto-tag donors as `donor`, `donor-monthly`, `campaign-123`
3. **Generic webhook** (Zapier / Make / n8n) — POST a JSON payload to any HTTP endpoint

All three use `wp_remote_post` with `blocking => false` so the donor's submit experience never stalls on a third-party API call.

## Implementation

- **`includes/Analytics/Privacy_Guard.php`** — allow-list sanitizers; the public contract any future v2.x analytics storage will run through.
- **`includes/Analytics/Submission_Tracker.php`** — server-side submit / fail hook; reads the new `dfwc_context` / `dfwc_currency` / `dfwc_language` hidden inputs the overlay JS injects so success / failure events carry render-time correlation data.
- **`includes/REST/Track_REST_Controller.php`** — `POST /wp-json/dfwc-companion/v1/track`, `__return_true` permission, rate-limited, batch-capped, allow-listed.
- **`assets/js/dfwc-overlay.js`** — `EventBuffer` module: 1s debounced flush, `fetch(..., { keepalive: true })` survives page unload, `pagehide` + `beforeunload` listeners flush proactively. Failures swallowed; analytics never breaks donor flow.
- **`includes/Frontend/Renderer.php`** + **`Context_Augmenter.php`** — wrapper now carries `data-context` (single / shortcode / widget / cart_block / preview / etc.) and `data-language` (WPML active or site locale).

## Backward compatibility

- Existing v1.0.x campaigns render unchanged. The new wrapper attributes are additive.
- Sites without listeners see zero behavior change — the track endpoint is registered but receives no traffic from sites that haven't wired anything.
- Hook signatures are stable through v1.x. The Guard's interface (and the implicit promise that PII never reaches `do_action`) is part of the v1.x contract.

## Test coverage

186 → **200+ cases**. New `Privacy_Guard_Test` (16 cases) covers the allow-list sanitizers + the PII-strip guarantee. The REST endpoint and Submission_Tracker are integration-tested via the contract suite rather than unit-tested in isolation (the WP REST infrastructure they touch isn't readily mockable in the bootstrap-stubs environment; the public contract is the Guard).
